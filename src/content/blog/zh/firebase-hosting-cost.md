## 要解决的问题

个人 Portfolio 的正常流量通常很低，Firebase Hosting 的免费额度基本足够，但升级到 Blaze 后，超过免费额度的使用会继续产生费用。相比正常访问带来的少量成本，我更关心异常流量、错误配置或恶意请求是否可能带来不可预测的账单，因此需要在网站可用性和成本可控之间做出选择。

## 可选方案

- **A.** 保持 Spark 免费计划，在达到免费使用限制时接受网站暂时不可用。
- **B.** 升级到 Blaze，并使用 Budget Alert 监控费用。
- **C.** 使用 Blaze，同时对动态服务增加认证、rate limiting、资源限制和监控。
- **D.** 将静态 Portfolio 和未来可能产生较高成本的 Backend 或 AI 服务拆分到不同项目中。

## 方案权衡

**A** 的可用性上限较低，但成本最容易控制。对于当前的静态 Portfolio，我更愿意在极端情况下暂时不可用，而不是承担不可预测的按量费用。

**B** 可以让 Hosting 在超过免费额度后继续运行，但 Budget Alert 只是费用提醒，并不是硬性消费上限，因此不能完全防止异常账单。

**C** 更适合真正需要 Cloud Functions、Cloud Run、数据库或 AI 服务的应用。动态服务的单次请求可能同时产生网络、计算和第三方 API 成本，因此需要额外的应用层保护。

**D** 可以进一步隔离成本风险，让公开 Portfolio 和更高成本的后台服务拥有独立的资源和预算边界。

对于当前项目，我选择继续使用 Spark。现阶段 Portfolio 并不需要 Blaze 提供的能力，因此没有必要为了更高的可用性提前承担按量计费风险。

## 潜在风险

- Spark 达到免费使用限制后，网站可能暂时无法继续正常提供服务。
- 如果未来升级到 Blaze，异常流量可能在费用提醒到达之前已经产生额外费用，因为 Budget Alert 不是实时的消费上限。
- 大型静态资源、错误的缓存配置以及异常请求都可能增加数据传输量。
- 如果未来加入 Backend、Database 或 AI API，成本风险会明显高于纯静态 Hosting，因此不能只依赖 Billing 设置，还需要认证、限流、资源限制和监控。

## 成功指标

- Portfolio 在正常流量下能够长期保持在免费使用范围内。
- 当前部署不需要为了暂时用不到的功能进入按量计费模式。
- 如果未来升级到 Blaze，能够清楚监控资源使用和费用变化，并对高成本服务增加必要的限制。
- 静态 Portfolio 和未来更高成本的 Backend 或 AI workload 能够进行风险隔离。
- 部署方案能够在可用性、维护复杂度和最坏情况下的账单风险之间保持合理平衡。
